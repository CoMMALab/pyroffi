## Gotchas (folded in — this file has no git history to re-read them from)

`EXPERIMENT_PLAN.md` was never committed, so the "re-read them from
`git show HEAD:iosp/EXPERIMENT_PLAN.md`" instruction above cannot be
followed; the list below is the one this file's own "Infrastructure to
RETAIN" section enumerates, written out in full so it survives.

- **ptxas fusion-disable.** Every IOSP config sets
  `XLA_FLAGS: --xla_disable_hlo_passes=fusion`. Without it, large-batch
  compiles hit ptxas' O(n²) pathology and hang rather than fail. Keep this
  in any new config.
- **Compilation cache.** `iosp/data/jax_cache/` is the persistent XLA cache.
  First compile of a tetris/tower segment residual takes 3-5 minutes and
  emits `slow_operation_alarm` — that is expected, not a failure. Do not
  kill a run that looks stalled before ~10 minutes of wall clock.
- **GPU contention.** `iosp/run_experiment.py::pick_gpu` refuses to launch
  when every GPU has >100 MiB in use. Check
  `nvidia-smi --query-gpu=index,memory.used,memory.total,utilization.gpu
  --format=csv` before a manual launch and pin with `--gpu <idx>`.
- **float32 only for IOSP.** Unlike `ioc.collect` (which forces
  `JAX_ENABLE_X64=1`), the IOSP experiments run in float32. Do not "fix" a
  residual by turning x64 on — it changes the forward solver's noise floor
  and invalidates comparison against existing results.
- **≥5 seeds.** Contact/solver nondeterminism moves residuals run-to-run;
  fewer than 5 seeds is not a measurement. `multistart_robustness.yaml` and
  `pickplace_iosp.yaml` use 5; `tetris_iosp.yaml`/`tower_iosp.yaml` use 3
  per difficulty level and should be raised to 5 before the table is final.
- **Fixed step budget.** Report at a fixed outer-step budget (`n_steps: 40`
  across every config), never at "convergence" — the fits peak rather than
  converge, so a convergence-based stopping rule silently changes the
  comparison.
- **Behavioural metrics over `param_err`.** Held-out EE RMSE and normalised
  regret are the criteria; `\|\Delta\theta\|` is context only. Along
  near-null eigendirections of the feature Gram matrix a large `param_err`
  is expected and is not a recovery failure — that is exactly what
  `fig_eigenspectrum` exists to show.
